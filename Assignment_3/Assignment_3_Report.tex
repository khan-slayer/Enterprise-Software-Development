\section{Architecture and Shared vs.\ Per-Replica State (Part A)}
We extended the Assignment 2 Bookstore system to run \textbf{three identical application replicas (A, B, C)} via Docker Compose scaling (\texttt{deploy.replicas: 3} on service \texttt{app}, exposing internal ports \texttt{8000} and \texttt{50051}). Each replica runs FastAPI (HTTP) and the gRPC server (\texttt{BookService} and \texttt{grpc.health.v1.Health}) in a single Python process with a unified Prometheus registry (\texttt{metrics.py}). On startup, each replica resolves its identity (\texttt{A}, \texttt{B}, \texttt{C}) via DNS lookup against \texttt{bookstore-app-1..3}, adds \texttt{replica} and \texttt{request\_id} to all JSON logs, and returns \texttt{x-replica-id} and \texttt{x-request-id} in HTTP response headers and gRPC initial/trailing metadata.

\begin{center}
\texttt{HTTP/gRPC Clients $\longrightarrow$ Envoy (:8080 HTTP, :50051 HTTP/2 gRPC) $\longrightarrow$ Replicas A, B, C $\longrightarrow$ Shared SQLite (WAL)}
\end{center}

Prometheus (\texttt{:9090}) scrapes Replicas A, B, C (\texttt{:8000/metrics}) and Envoy (\texttt{:9901/stats/prometheus}) \textbf{directly} every 5s. Filebeat ships container JSON logs from \texttt{envoy} and \texttt{app} replicas to Elasticsearch (\texttt{:9200}).

\section{Baselines (Parts B \& C)}
All runs used \texttt{fixed\_rate\_client.py} (open-loop \texttt{asyncio} ticker at 20.0 req/s, retries and circuit breakers disabled, single shared HTTP/2 connection for gRPC, querying \texttt{GET /books/1} and \texttt{GetBook(id=1)}).
\begin{itemize}
    \item \textbf{Part B (A-Only):} 100\% of HTTP (400/400, p50=14.88\,ms, p95=51.81\,ms) and gRPC (400/400, p50=11.98\,ms,\linebreak p95=24.28\,ms) went to Replica A; B and C remained idle.
    \item \textbf{Part C (Equal Round Robin 1:1:1):} HTTP split \textbf{33.08\% / 33.58\% / 33.33\%} (p95 improved 51.81$\to$36.31\,ms across 3 event loops); gRPC split \textbf{33.25\% / 33.25\% / 33.50\%} (p95=23.12\,ms, 0\% error).
    \item \textbf{Why HTTP/2 on Envoy's gRPC Listener Matters:} A gRPC client multiplexes all calls over one persistent connection. Plain TCP (L4) proxying pins the entire connection to one backend. Setting \texttt{codec\_type: HTTP2} lets Envoy inspect individual HTTP/2 streams and balance \textbf{per RPC call} across A, B, and C.
\end{itemize}

\begin{enumerate}
    \item \textbf{Weighted Round Robin (2:1:1):}
    \textbf{Prediction:} Replicas A, B, and C will receive 50\%, 25\%, and 25\% of traffic respectively; at 20 req/s on a single host with ample CPU headroom, latency should remain near the 1:1:1 baseline.
    \textbf{Observations:} HTTP split \textbf{50.25\% / 24.75\% / 25.00\%} (p50=13.25\,ms, p95=38.30\,ms); gRPC split \textbf{50.00\% / 25.00\% / 25.00\%} (p50=12.08\,ms, p95=21.52\,ms), with 0\% errors and A handling $2\times$ the request rate of B or C.
    \textbf{Explanation:} Envoy's weighted round-robin scheduler enforces the 2:1:1 ratio deterministically, while a higher weight does not add CPU/DB capacity---because all replicas were lightly loaded, latency did not degrade (under saturation, A would bottleneck first).

    \item \textbf{Least Request vs.\ Round Robin (Slow Replica B +250\,ms):}
    \textbf{Prediction:} Round Robin will keep sending 33.3\% of calls to B regardless of latency, inflating p50 and p95. Least Request (\texttt{choice\_count: 2}) will observe higher active in-flight requests on B and shift traffic to A and C, lowering B's share and mean/p50 latency.
    \textbf{Observations:} Under RR, B received 33.25\% (HTTP p50=22.32\,ms, p95=275.44\,ms; gRPC p50=22.10\,ms, p95=275.19\,ms). Under Least Request, B's active requests spiked to 2 (vs.\ 0--1 on A/C) and B's share dropped to \textbf{17.50\%} (HTTP) and \textbf{17.75\%} (gRPC), reducing p50 to \textbf{14.68\,ms} (HTTP) / \textbf{14.33\,ms} (gRPC) and mean latency from $\sim$103\,ms to $\sim$63\,ms, while p95 stayed near 273\,ms.
    \textbf{Explanation:} B's 250\,ms service time keeps requests in flight $\sim$15$\times$ longer than A/C, so power-of-two choices picks the less-busy replica (A or C) most of the time; because $>5\%$ of calls still land on B, p95 remains bounded by the 250\,ms fault.

    \item \textbf{Failure \& Recovery with Active Health Checks:}
    \textbf{Prediction:} Stopping B will cause brief errors for $\sim$2--4\,s until 2 consecutive health checks fail (\texttt{interval: 2s, unhealthy\_threshold: 2}), after which Envoy ejects B and shifts 100\% of traffic to A and C; restarting B will restore it after container boot plus 2 healthy checks.
    \textbf{Observations:} Stopping \texttt{bookstore-app-2} at $t\approx 8\text{s}$ and restarting at $t=20\text{s}$ shifted traffic to A/C ($\sim$45--46\% each). For gRPC, errors occurred only between $t=8.589\text{s}$ and $12.906\text{s}$ (\textbf{4.32\,s}, 33 \texttt{UNAVAILABLE} errors, 4.58\%); for HTTP, 187 \texttt{503}s (25.97\%) occurred across stop and DNS-refresh intervals.
    \textbf{Explanation:} The 4.32\,s gRPC error window matches \texttt{interval=2s $\times$ unhealthy\_threshold=2}. Upon restart at $t=20\text{s}$, Python/Uvicorn boot ($\sim$3\,s) plus \texttt{healthy\_threshold=2} ($\sim$4\,s) and \texttt{STRICT\_DNS} refresh restored B to 3/3 healthy right at the end of the 36\,s window.
\end{enumerate}

\section{Conclusions}
\begin{enumerate}
    \item \textbf{Chosen Strategy:} \textbf{Least Request + Active Health Checks} for both HTTP and gRPC. It matches Round Robin when replicas are healthy, automatically cuts slow-replica traffic in half (33.25\%$\to$17.5\%) under latency degradation, and ejects dead backends in $\sim$4.3\,s.
    \item \textbf{Different Workload:} For stateful or cache-affine workloads (e.g., per-book in-memory LRU caching), \textbf{Consistent Hashing (\texttt{RING\_HASH})} on \texttt{book\_id} or user key would maximize cache hit rates.
    \item \textbf{If Envoy Stops:} Envoy is a single point of failure; all client traffic fails even though A, B, C are healthy. \textbf{Improvement:} Run active-active Envoy pairs behind a Virtual IP (\texttt{keepalived}/VRRP) or a cloud L4 NLB.
\end{enumerate}
